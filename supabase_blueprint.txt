# SILVERLINE RESORT — SUPABASE DATABASE BLUEPRINT
**Based on complete code inspection — READ ONLY — DO NOT EXECUTE**
**Inspected:** All files in api/, api/_lib/, data/, js/, scripts/, pages/, config files

---

## 1. Executive Summary

The Silverline Resort application uses 7 JSON flat files for persistence. Every single one maps cleanly to a PostgreSQL table with no structural redesign required. The schema is already well-normalised in the code — `reservations` references `guests` by `guestId`, and `payments` references `reservations` by `reservationId`. The only additions needed are:

1. **PostgreSQL ENUM types** for statuses (already well-defined in the code)
2. **`updated_at` auto-triggers** (the code manually sets `updatedAt` — move this to DB)
3. **`SELECT FOR UPDATE` transaction pattern** in the booking API to replace the race-prone JSON read/write
4. **Row Level Security (RLS)** — all tables must be server-side only (Supabase service role key via the API layer, no direct public access)
5. **`settings` table** — the single JSON object maps best to a JSONB column with a singleton row (`id = 1`)

No additional tables (e.g., `room_inventory`, `rate_plans`, `reservation_rooms`) are required based on the current application code. The existing model uses **room type inventory as a count** (`room_types.inventory INT`) — there are no individual physical room records. This is the correct model for this property size.

### TABLE: `settings`
**Purpose:** Singleton hotel configuration. Stored as a nested JSONB object. Currently read by `getSettings()` on every API call. Updated via `PATCH /api/admin/settings`.

| Column | PostgreSQL Type | Nullable | Default | PK | FK | Description |
|---|---|---|---|---|---|---|
| `id` | `SMALLINT` | NOT NULL | `1` | ✅ | — | Always 1 (singleton row) |
| `hotel` | `JSONB` | NOT NULL | `'{}'` | — | — | Hotel name, phone, email, address, check-in/out times, timezone |
| `pricing` | `JSONB` | NOT NULL | `'{}'` | — | — | taxRate, taxLabel, serviceFee, minNights, maxNights, advanceBookingDays |
| `notifications` | `JSONB` | NOT NULL | `'{}'` | — | — | emailProvider, smsProvider, sendConfirmation, sendCancellation, sendReminder |
| `ota` | `JSONB` | NOT NULL | `'{}'` | — | — | provider, agodaUrl, ixigoUrl |
| `payment` | `JSONB` | NOT NULL | `'{}'` | — | — | provider, supportedMethods, testMode |
| `updated_at` | `TIMESTAMPTZ` | NOT NULL | `now()` | — | — | Last settings update |

**Why JSONB instead of flat columns?**
The `settings.json` structure has deeply nested objects (`hotel`, `pricing`, `notifications`, etc.) that the application reads as a whole and partially updates. The admin API does deep-merge updates at the section level. JSONB preserves this exactly and allows the `updateSettings()` function's merge pattern to translate directly to a PostgreSQL `jsonb_set()` or `||` merge operator. Adding a new settings key does not require a schema migration.

**Constraint:**
- `CHECK (id = 1)` — enforces singleton

### TABLE: `audit_logs`
**Purpose:** Immutable append-only event log. Written by `appendAuditLog()` across all API operations — login, reservation create/update, settings change, room update, logout. Never updated or deleted.

| Column | PostgreSQL Type | Nullable | Default | PK | FK | Description |
|---|---|---|---|---|---|---|
| `id` | `BIGSERIAL` | NOT NULL | auto | ✅ | — | Auto-increment integer (not UUID — high volume, sequential) |
| `user_id` | `UUID` | NULL | `NULL` | — | `users.id` (no FK constraint — see note) | Admin user ID, NULL for guest actions |
| `action` | `TEXT` | NOT NULL | — | — | — | Event type string (see list below) |
| `resource` | `TEXT` | NOT NULL | — | — | — | Resource type: reservation, auth, settings, room_type |
| `resource_id` | `TEXT` | NULL | `NULL` | — | — | ID of affected resource (UUID as text — polymorphic) |
| `meta` | `JSONB` | NULL | `NULL` | — | — | Event-specific metadata (booking ref, email, IP, etc.) |
| `timestamp` | `TIMESTAMPTZ` | NOT NULL | `now()` | — | — | When event occurred |

**Why BIGSERIAL not UUID for id?** Audit logs are appended at high frequency. Sequential integer IDs are faster to insert and index for time-based queries.

**Why no FK on `user_id`?** Audit logs are immutable history. If an admin account is deleted, you must not lose the audit trail. Use `NULL` for deleted users, not a FK constraint that would block deletion.

**Why TEXT for `resource_id`?** The resource ID can be a UUID (reservation, guest, user) or a text slug (`room_type`: `standard-room`). Using TEXT avoids type mismatch.

## 4. Relationships

```
users (id)
  │
  ├──→ audit_logs (user_id)     [1 user : many log entries, nullable]
  │
  └──→ reservations (updated_by)  [1 user : many reservations, nullable — admin updates]

guests (id)
  │
  └──→ reservations (guest_id)   [1 guest : many reservations]
          │
          └──→ payments (reservation_id)   [1 reservation : 1 payment (current design)]

room_types (id)
  │
  └──→ reservations (room_type_id)  [1 room_type : many reservations]

settings  [standalone singleton — no FK relationships]
audit_logs [standalone append-only — soft FK on user_id only]
```

### Relationship Detail

| Parent | Child | FK Column | Cardinality | ON DELETE | Why |
|---|---|---|---|---|---|
| `guests` | `reservations` | `guest_id` | 1:many | `RESTRICT` | Can't delete guest with bookings |
| `room_types` | `reservations` | `room_type_id` | 1:many | `RESTRICT` | Can't delete room type with history |
| `users` | `reservations` | `updated_by` | 1:many | `SET NULL` | Admin deletion shouldn't erase reservation history |
| `reservations` | `payments` | `reservation_id` | 1:1 (current) | `CASCADE` | Payment meaningless without reservation |

## 9. Double-Booking Protection

### Current Problem (JSON File System)
The current code does:
1. `readJson('reservations.json')` → count overlaps
2. If available → `writeJson('reservations.json', newReservation)`

Between steps 1 and 2, another concurrent request can read the same state, both see "available", both write — creating a double booking.

### Why This Is Dangerous for Production
The `countOverlappingBookings()` function in `api/_lib/availability.js` uses the formula:
```
ci < ro && co > ri   (where ci/co = new checkIn/checkOut, ri/ro = existing checkIn/checkOut)
```
This logic is **correct**. The problem is not the logic — it's the non-atomic storage.

### Recommended Production Solution: PostgreSQL Transaction + SELECT FOR UPDATE + Count Validation

**Pattern to use in the new `api/reservations.js`:**

```sql
-- All of this runs inside a single transaction
BEGIN;

-- Step 1: Lock the room_types row to serialize concurrent bookings for this room type
SELECT inventory FROM room_types
WHERE id = $roomTypeId AND active = true
FOR UPDATE;

-- Step 2: Count existing overlapping reservations (within the same transaction)
SELECT COUNT(*) AS booked
FROM reservations
WHERE room_type_id = $roomTypeId
  AND status NOT IN ('cancelled', 'no-show')
  AND check_in  < $checkOut::date
  AND check_out > $checkIn::date;

-- Step 3: Application checks: if booked >= inventory → ROLLBACK and return 409
-- Step 4: If available → INSERT reservation + INSERT payment

COMMIT;
```

**Why `SELECT FOR UPDATE` on `room_types`?**
- It places a row-level exclusive lock on the specific room type row
- Any second concurrent transaction trying to `SELECT FOR UPDATE` the same row will **block** until the first transaction commits or rolls back
- This serialises concurrent bookings for the same room type
- Bookings for different room types proceed independently (no global lock)

**Why not PostgreSQL exclusion constraints?**
An exclusion constraint using `tsrange` (timestamp range type) would be ideal if inventory was 1 unit per room. But this property has 2–3 units per room type (e.g., `standard-room` has inventory 3). An exclusion constraint would prevent ANY overlap for the same room_type_id, which is too restrictive. The `SELECT FOR UPDATE + COUNT` pattern handles the inventory count correctly.

**Why not application-level Redis locks?**
That would add infrastructure complexity (Redis) that is not present in the current stack. PostgreSQL transactions are sufficient and the correct tool here.

**Summary of architecture change for booking atomicity:**
- Use `@supabase/supabase-js` with `rpc()` to call a PostgreSQL function that runs the entire booking as a single transaction
- Or use Supabase's `pg` connection with explicit `BEGIN/COMMIT`
- The `api/reservations.js` file becomes the only place that calls this transaction
- The `validateFinalAvailability()` function in `api/_lib/availability.js` is replaced by the SQL count inside the transaction

## 10. Supabase RLS / Security

### The Security Model

The application is a **server-side rendered + serverless API** system. All data access goes through Vercel serverless functions (`api/*.js`) using the **Supabase service role key**. The browser never talks to Supabase directly.

```
Browser → Vercel API (api/reservations.js) → Supabase (service_role key)
```

### RLS Configuration

| Table | RLS Enabled | Public SELECT | Public INSERT | Public UPDATE | Public DELETE | Reasoning |
|---|---|---|---|---|---|---|
| `guests` | ✅ YES | ❌ NO | ❌ NO | ❌ NO | ❌ NO | PII — server-side only |
| `room_types` | ✅ YES | ✅ YES (active only) | ❌ NO | ❌ NO | ❌ NO | Room catalogue is public data |
| `reservations` | ✅ YES | ❌ NO | ❌ NO | ❌ NO | ❌ NO | Booking data — server-side only |
| `payments` | ✅ YES | ❌ NO | ❌ NO | ❌ NO | ❌ NO | Payment data — server-side only |
| `users` | ✅ YES | ❌ NO | ❌ NO | ❌ NO | ❌ NO | Auth — server-side only |
| `settings` | ✅ YES | ✅ YES (pricing/hotel only) | ❌ NO | ❌ NO | ❌ NO | Hotel name/check-in times are public info |
| `audit_logs` | ✅ YES | ❌ NO | ❌ NO | ❌ NO | ❌ NO | Internal only |

### Access Pattern

```sql
-- Most tables: deny all public access
CREATE POLICY "deny_public_access"
  ON reservations FOR ALL
  TO anon, authenticated
  USING (false);

-- room_types: allow public to read active rooms only
CREATE POLICY "public_read_active_rooms"
  ON room_types FOR SELECT
  TO anon
  USING (active = true);

-- All data access from API goes through service_role key
-- Service role bypasses ALL RLS policies
-- NEVER expose the service_role key to frontend JavaScript
```

### Key Points
- **`SUPABASE_SERVICE_ROLE_KEY`** — only used in Vercel serverless functions (server environment). NEVER in frontend JS.
- **`SUPABASE_ANON_KEY`** — safe for frontend, but since all API calls go through serverless functions, the anon key is not needed in frontend at all.
- The admin JWT authentication continues to be handled by `api/_lib/auth.js` (application layer) — Supabase Auth is NOT being used. The existing bcrypt + JWT system is kept as-is.

  p_booking_reference TEXT,

  p_guest_name        TEXT,
  p_guest_email       TEXT,
  p_guest_phone       TEXT,

  v_inventory   SMALLINT;
  v_booked      INTEGER;
  v_available   INTEGER;

  -- Lock the room type row to serialise concurrent bookings
  SELECT inventory INTO v_inventory
  FROM room_types
  WHERE id = p_room_type_id AND active = true
  FOR UPDATE;

  IF NOT FOUND THEN
    RETURN jsonb_build_object('ok', false, 'reason', 'Room type not found or inactive.');
  END IF;

  SELECT COUNT(*) INTO v_booked
  FROM reservations
  WHERE room_type_id = p_room_type_id
    AND status NOT IN ('cancelled', 'no-show')
    AND check_in  < p_check_out
    AND check_out > p_check_in;

  v_available := v_inventory - v_booked;

  IF v_available <= 0 THEN
    RETURN jsonb_build_object('ok', false, 'reason', 'This room is no longer available for your selected dates.');
  END IF;

    id, booking_reference, guest_id, guest_name, guest_email, guest_phone,
    room_type_id, room_type_name, check_in, check_out, nights, adults, children,
    special_requests, base_price, subtotal, taxes, total, tax_rate,
    currency, status, payment_status, payment_provider, payment_reference

    p_id, p_booking_reference, p_guest_id, p_guest_name, p_guest_email, p_guest_phone,
    p_room_type_id, p_room_type_name, p_check_in, p_check_out, p_nights, p_adults, p_children,

    'INR', 'confirmed', 'paid', p_payment_provider, p_payment_reference
  );

  -- Insert payment record
  INSERT INTO payments (
    id, reservation_id, booking_reference, provider,
    order_id, transaction_id, amount, currency, status, test_mode
  ) VALUES (
    p_payment_id, p_id, p_booking_reference, p_payment_provider,
    p_order_id, p_transaction_id, p_amount, 'INR', 'captured', p_test_mode
  );

  RETURN jsonb_build_object('ok', true, 'booking_reference', p_booking_reference);

EXCEPTION WHEN OTHERS THEN
  RETURN jsonb_build_object('ok', false, 'reason', SQLERRM);
END;
$$;
